# DLSM 大对象（LOB）存储设计

> **状态：预留设计（Phase 4+，暂不实现）。**
> TPC-C 无大对象，不在 P1–P3 关键路径上。本文档锁定设计决策与 locator 预留格式，
> 以便行编码留出位置；具体实现推迟到 Phase 4。

## 一、背景

现有两层存储都不适合大对象（TEXT/BYTE/JSON/二进制等）：

- **Delta Log（热）**：顺序日志 + 4KB 节点颗粒度，承载大对象会严重写放大。
- **Vortex（冷，列存）**：列式压缩对结构化列有效，对一坨二进制大对象无意义。

故新增**第三类存储空间——大对象空间**，与冷热行存储正交。

## 二、存储分层（含本设计）

| 存储层 | 后端 | 适合的数据 | 颗粒度 |
|--------|------|-----------|--------|
| Hot (Delta Log) | 顺序日志文件 | 热行、小值、版本链 | 行/版本 |
| Cold (Vortex) | 列存文件 | 冷的结构化列、OLAP 扫描 | row group |
| **大对象空间** | 本地可变空间 / 对象存储 | 超阈值的大对象 | 单个对象 |

## 三、核心决策

1. **分层混合**：热大对象放**本地可变空间**（支持流式写入、部分更新、seek 随机读写）；
   冷大对象下沉到 **S3-like 不可变对象存储**（每个对象/版本即一个不可变 object）。
   镜像现有 Delta Log → Vortex 的冷热分层。locator 携带 **tier 位**区分两者。

2. **行内 vs 行外阈值**：小值仍内联在 Delta Log 行记录里；超过阈值才**外置**到大对象空间，
   行记录里只留一个 **locator**。

3. **locator 为列级**：大对象是**列属性**而非行属性（一行可能只有某列是大对象），
   故 locator 存在行记录的对应列位置，**不**给 `DeltaPointer` 增加变体
   （见架构决策 #10：`DeltaPointer` 是引擎内部 enum，但大对象定位属于列编码层）。

4. **下沉触发——跟随行/页冷化**：当 owning 行/节点被 consolidate/flush 到 Vortex 冷层时，
   其大对象一并迁移到对象存储。复用现有冷热判定，生命周期与行一致，无需独立后台扫描器。

5. **崩溃恢复——仅 locator 进 redo**：大对象数据**不进 WAL**（避免 GB 级负载撑爆日志与 fsync）。
   写入顺序：大对象先落盘（本地可变空间）/ 先上传（对象存储）→ 再把 locator 写进行记录进 redo。
   commit 时大对象数据已持久化；恢复只需重放 locator。

## 四、Locator 预留格式（字段细节待实现期定稿）

列级大对象 locator，概念字段：

- `tier`：`HotLocal` | `ColdObject`
- `space_id`：所属大对象空间 ID
- `object_id`：本地空间内对象 ID（HotLocal）/ 对象存储 key（ColdObject）
- `length`：对象字节长度
- （可选）`checksum`：完整性校验

## 五、大对象空间抽象（预留）

- **大对象空间** = 命名存储区，含 `id` + 后端类型（`local-mutable` | `object-store`）+ 后端配置
  （本地路径 / bucket + endpoint + 凭证）。
- 表/列可映射到指定空间（默认空间 + 可覆盖）。

## 六、待实现期细化（开放项）

- 流式读写 API（open / seek / read / write 句柄，针对 HotLocal）。
- 本地可变空间的物理布局（元数据区 + 用户数据区 + 空闲管理）。
- 对象存储侧的版本与 GC 如何与 Epoch GC 协作（不可变对象的旧版本回收）。
- 行外阈值、下沉判定参数的默认值与可配置项。
